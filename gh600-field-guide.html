GH-600 Field Guide: the how-to companion to the study pack. Each section shows the full process for one exam domain: a diagram of the flow, a numbered walkthrough, and the actual files and commands you would write. Works offline.

Naming drift: GitHub Docs now call the product the Copilot cloud agent. "Copilot coding agent" (CCA) is the earlier name and still appears in older material — and possibly in exam items written before the rename. Treat the two as exact synonyms. This guide uses "coding agent" throughout; every statement applies equally under either name.

Quick reference: the 10 facts that decide exam questions

1. The lifecycle

  • Plan → Act → Evaluate (cyclical)
  • Agents propose; humans + policy decide

2. Never merge to main

  • Own branch, open a PR, let checks + review gate
  • No direct pushes, no self-merges

3. Least privilege per role

  • Planner: tools: ['read','search']
  • Executor: tools: ['read','search','edit','execute']

4. MCP allow list layering

  • Org policy → Registry → Server → Tool
  • "Registry only" blocks unlisted servers

5. Durable memory = platform

  • Issues, PRs, commits, checks, artefacts
  • Context window is ephemeral; resume from the record

6. Root-cause → tuning lever

  • Reasoning error → revise instructions
  • Tool misuse → refine tool access
  • Context/env → refine memory scope

7. Permissions block zeroes the rest

  • Specifying one scope sets all others to none
  • Use job-level, not workflow-level

8. Two reviews, two kinds

  • Copilot review: automatic, advisory
  • CODEOWNERS review: human, required for merge

9. Merge gate ≠ deploy gate

  • Rulesets + checks → guards what enters main
  • Environment protection → guards what reaches prod

10. Velocity balance

  • Gate irreversible/compliance-sensitive actions
  • Don't gate low-risk actions; speed matters

The full process end to end

Every domain in GH-600 is a slice of one lifecycle: an issue arrives, a plan is produced and approved, an agent implements, the platform verifies, humans and policy gate, and only then does anything reach production. Exam questions jump into the middle of this pipeline and ask "what happens next?" or "which control stops this?", so hold the whole story as a single picture.

The process

  1. An issue arrives (D1). The issue is the system of record for intent: inputs, expected outputs, and success criteria.

  2. A planner agent produces plan.md (D1). The planner is read-only. Output is a structured plan committed as an inspectable artefact.

  3. A human approves the plan (D6). No action until the plan is checked and approved.

  4. A coder agent implements on its own branch (D2). Write access, isolated branch, tightly scoped workflow permissions, never direct to main.

  5. A PR opens from a template (D1 artefact, D6 governance). The PR is the anchor record. Template lives at .github/pull_request_template.md.

  6. Required checks and reviews run (D4 signals, D6 gates). CodeQL and secret scanning are required. Copilot review runs automatically. CODEOWNERS pulls in accountable humans.

  7. Ruleset, deployment gate, production (D6). Branch ruleset requires checks and CODEOWNERS review. Environment protection requires named approver before production deploy.

The speaker's one-liner: "evaluate the work by the standards of the workflow, not by the novelty of the author". Every gate already existed for humans; agentic development reuses them.

Gotchas and exam tips

  • Order matters. Plan, approve, act, verify, gate, deploy.
  • Read-only planner, write-scoped executor.
  • Merge gate and deployment gate are different controls. Rulesets govern what enters main; environment protection governs what reaches production.
  • The PR is the anchor, not the agent's memory.
  • Two reviews, two kinds. Copilot PR review never satisfies a required-review rule.

Domain 1 how-to: wire agents into the SDLC

Domain 1 (15–20%) is about making an agent behave like a well-run contributor: structured task, readable plan, approval gate, own branch, PR that the workflow validates. The lifecycle is plan, act, evaluate — cyclical, not linear.

The process

  1. Define the task as a structured issue. Three required fields: inputs, outputs, and success criteria. Encode as an issue form (.github/ISSUE_TEMPLATE/agent-task.yml).

    .github/ISSUE_TEMPLATE/agent-task.yml 
    name: Agent task
description: Delegate a scoped task to a coding agent
title: "[agent] "
labels: ["agent-task"]
body:
  - type: textarea
    id: inputs
    attributes:
      label: Inputs
      description: Files, paths, APIs and constraints the agent may use
    validations:
      required: true
  - type: textarea
    id: outputs
    attributes:
      label: Expected outputs
      description: Artefacts the agent must produce
    validations:
      required: true
  - type: textarea
    id: success
    attributes:
      label: Success criteria
      description: Measurable conditions that mean the task is done
    validations:
      required: true
  - type: dropdown
    id: autonomy
    attributes:
      label: Autonomy level
      options:
        - Plan only (await approval)
        - Plan then execute after approval
    validations:
      required: true

  2. Make the agent plan before it acts. The planner writes plan.md to its task branch and stops. Planner agents should be read-only.

  3. Gate execution on plan approval. A human approves the plan before the agent writes any code.

  4. Execute on an isolated branch, one PR per task. Branch naming convention: agent/142-fix-invoice-rounding. Never merge directly to main.

  5. Validate by the standards of the workflow. Required Actions checks run, agent gathers evidence, failures feed back into execution.

Gotchas and exam tips

  • "Never merge directly to main" is a marked exam point.
  • Know the three anti-patterns: execution without validation, no separation between planning and execution, unbounded autonomy with no inspectable artefacts.
  • The plan is an artefact, not a chat message.
  • Durable state lives in GitHub records, not the agent.

Domain 2 how-to: tools, MCP servers and safe execution

The heaviest domain (20–25%). Mental model: agents operate through the platform, not around it. MCP (Model Context Protocol) is the standardised layer for tool discovery and results.

The process

  1. Identify the tools the task actually needs. Map each need to a tool or MCP server. Everything else stays off.

  2. Add the GitHub remote MCP server to your workspace. For local VS Code, use .vscode/mcp.json (top-level key: servers, type: stdio or http).

  3. Configure MCP for the coding agent at the repository. Paste JSON into Settings > Copilot > MCP servers (top-level key: mcpServers, type: local or http).

  4. Fence it in at the organisation. Org admin sets an MCP registry URL and policy under Settings > Copilot > Policies. "Registry only" blocks unlisted servers.

  5. Define a custom agent with role boundaries. Markdown files in .github/agents/ with YAML frontmatter scoping capability.

  6. Give the CI workflow least-privilege permissions. Declare every scope explicitly at job level; unlisted scopes become none.

  7. Add timeouts, retries and an escalation path.

    .github/workflows/agent-task.yml 
    name: Agent task with safe execution
on:
  pull_request:
    types: [opened, synchronize]
permissions: {}
jobs:
  validate:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions:
      contents: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
      - name: Run checks with bounded retries
        timeout-minutes: 5
        run: |
          for attempt in 1 2 3; do
            npm test && exit 0
            echo "Attempt $attempt failed"
            sleep $((attempt * 10))
          done
          exit 1
      - name: Escalate to a human
        if: failure()
        run: |
          gh issue create \
            --title "Agent task failed on ${{ github.head_ref }}" \
            --body "Run: ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}"
        env:
          GH_TOKEN: ${{ secrets.ESCALATION_TOKEN }}

Key differences to memorise: .vscode/mcp.json uses "servers" and "type": "stdio". The cloud config uses "mcpServers" and "type": "local". Secrets in the cloud use the COPILOT_MCP_ prefix.

Where configs live (exam's favourite trick)

Gotchas and exam tips

  • The GitHub MCP server is on by default for the coding agent, read-only.
  • Know where each config lives. Expect distractors that swap locations.
  • Tools frontmatter semantics: omitted or ["*"] = all tools; list = only those; [] = none.
  • One permissions key zeroes the rest.

Domain 3 how-to: durable memory and resumable state

Domain 3 (10–15%). Agent execution is ephemeral: when a run ends, its context window is gone. GitHub is the durable memory. Make agent work resumable by writing state into the platform record.

The process

  1. Anchor the task to a pull request early. Create branch and open a draft PR as first act.

  2. Maintain a plan document on the branch and checkpoint decisions into it.

  3. Persist evidence as workflow artefacts, because logs expire.

  4. Write progress comments to the PR.

  5. Resume by reading the record, not by redoing the work.

  6. Scope memory to the task. Pull only what the current step needs.

  7. Detect context rot and prune or reset. Checkpoint decisions, post a status comment, reset the session, resume from the durable record.

Mental model: context window = short-term memory (volatile); issues, PRs, commits, checks, artefacts = long-term memory (durable, authoritative).

Gotchas and exam tips

  • "Resume" means read, never redo.
  • Logs expire; artefacts are the durable evidence.
  • Context rot fix-list: scope memory, prune, checkpoint, reset.
  • Reverted attempts are memory too. History showing a tried-and-reverted approach steers the agent away from repeating it.

Domain 4 how-to: evaluation signals and the tuning loop

Domain 4 (15–20%). Observe, detect, correct: quantitative signals from scan output and workflow results, classify the root cause, tune the agent, write findings back to the plan.

The process

  1. Wire up CodeQL so results arrive as checks. Add .github/workflows/codeql.yml. The analyze step uploads SARIF, which turns findings into a PR check.

    .github/workflows/codeql.yml 
    name: "CodeQL"
on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]
  schedule:
    - cron: "20 14 * * 1"
jobs:
  analyze:
    name: Analyze (${{ matrix.language }})
    runs-on: ubuntu-latest
    permissions:
      security-events: write
      contents: read
      actions: read
    strategy:
      matrix:
        include:
          - language: javascript-typescript
            build-mode: none
    steps:
      - uses: actions/checkout@v4
      - name: Initialize CodeQL
        uses: github/codeql-action/init@v4
        with:
          languages: ${{ matrix.language }}
          build-mode: ${{ matrix.build-mode }}
      - name: Perform CodeQL Analysis
        uses: github/codeql-action/analyze@v4
        with:
          category: "/language:${{ matrix.language }}"

  2. Enable secret scanning and push protection. Settings → Advanced Security. Push protection blocks a push containing a detectable secret before it lands.

  3. Make the checks required. Settings → Rules → Rulesets. Add CodeQL check to required list.

  4. Define success criteria in the plan document before the agent acts.

  5. Triage a failed run from the terminal.

  6. Classify the root cause. Reasoning error: wrong conclusion from correct inputs. Tool misuse: wrong tool or bad parameters. Context/environment: missing dependency, expired token, context rot.

  7. Tune the matching lever. Reasoning → revise instructions. Tool misuse → refine tool access. Context/env → refine memory scope.

  8. Write findings back to the plan and re-run.

Memorise the mapping: reasoning error → revise instructions; tool misuse → refine tool usage and access; context/environment → refine memory usage and fix the environment.

Gotchas and exam tips

  • Missing security-events: write is the classic reason a SARIF upload fails.
  • Push protection is preventative; secret scanning alerts after the fact.
  • A failing check only gates a merge if it is required via a ruleset.
  • Suppressing an alert to go green = reasoning error, not tool misuse.

Domain 5 how-to: build a multi-agent team

Domain 5 (15–20%). Four-role team: orchestrator, planner (read-only), coder and designer (execute in parallel). Each agent is a markdown file; isolation comes from branches and permissions; arbitration comes from CODEOWNERS.

The process

  1. Write one markdown profile per agent. Files in .github/agents/ (repo) or agents/ in the org's .github/.github-private repo (org-wide). Named <name>.agent.md.

  2. Scope permissions by role.

  3. Isolate execution with per-agent branches and concurrency groups.

  4. Arbitrate overlapping areas with CODEOWNERS.

  5. Document every handoff so post-hoc analysis works.

  6. Detect stalled or partial runs, then recover safely. Rollback = revert the branch or close the PR. Resume = read the PR, checks, commits. Escalate via CODEOWNERS.

  7. Manage the lifecycle without breaking the workflow. Adding: new profile + branch prefix + CODEOWNERS line. Retiring: remove the profile, keep closed PRs and commit history.

Gotchas and exam tips

  • Least privilege is the banker question: planning agents are read-only.
  • Agents never merge to main.
  • CODEOWNERS precedence: last matching pattern wins. File found in .github/, then root, then docs/.
  • Concurrency: cancel-in-progress: true kills the old run; false queues the new one.
  • Conflict resolution is GitHub-native via CODEOWNERS, not agents negotiating.

Domain 6 how-to: install the guardrails

Domain 6 (10–15%). Governance as switches you flip in three places: repository settings, files in .github/, and workflow YAML. Know which control lives where, and right-size each gate to the risk of the action it guards.

The process

  1. Classify actions by risk before building any gate.

    Risk classExample actionsGate
    LowFormat code, update docs on a branchAutomated checks only
    MediumChange app code, bump a dependencyRuleset: PR + checks + Copilot review
    HighTouch auth or payment paths, edit CI configCODEOWNERS + code owner review rule
    CriticalProduction deploy, data deletion, secret rotationEnvironment gate or blocked entirely

  2. Create a ruleset to guard the default branch. Settings → Rules → Rulesets → New branch ruleset. Set enforcement to Active, target default branch, require PR before merging.

  3. Add required status checks and automatic Copilot review.

    Importable ruleset JSON 
    {
  "name": "agent-guardrails",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] }
  },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    {
      "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 1,
        "require_code_owner_review": true,
        "dismiss_stale_reviews_on_push": true,
        "required_review_thread_resolution": true,
        "allowed_merge_methods": ["squash"]
      }
    },
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": true,
        "required_status_checks": [
          { "context": "Analyze (javascript-typescript)" },
          { "context": "validate" }
        ]
      }
    },
    {
      "type": "copilot_code_review",
      "parameters": { "review_on_push": true, "review_draft_pull_requests": false }
    }
  ]
}

  4. Map human ownership for high-risk paths via CODEOWNERS.

  5. Protect the deployment environment. Settings → Environments → New environment → Required reviewers.

  6. Scope the GITHUB_TOKEN to least privilege.

  7. Prune for velocity, then check the audit trail. Remove approvals that don't materially reduce risk. Verify accountability end to end.

Velocity balance is examined, not just gating. If an answer option adds human approval to every low-risk action, it is usually wrong.

Gotchas and exam tips

  • Copilot code review is a standalone ruleset rule; its approval never counts toward required_approving_review_count.
  • The permissions: trap: specifying even one scope silently sets all others to none.
  • Environment protection rules are configured only in Settings → Environments; the YAML environment: key just points at them.
  • Use ~DEFAULT_BRANCH in ruleset conditions rather than hardcoding refs/heads/main.

Domain 2: Tools & MCP

Q1. A developer wants the Copilot coding agent to use a Playwright MCP server when working on their repository. Where should they add the MCP server configuration?

  1. In .vscode/mcp.json committed to the repository
  2. In the repository's Settings > Copilot > MCP servers
  3. In the organisation's Copilot policies page
  4. In the agent's .agent.md file under mcp-servers

Answer: B. The cloud-based coding agent does not read .vscode/mcp.json — that's for the local IDE only. The org policies page (C) controls allow lists, not individual server configs. An agent profile (D) can embed mcp-servers, but the standard repo-wide approach is Settings > Copilot > MCP servers.

Q2. An organisation admin wants to ensure agents can only use MCP servers that have been vetted by the security team. What should they configure?

  1. Set each agent's tools: field to an empty array
  2. Remove all MCP server entries from .vscode/mcp.json
  3. Set the Copilot MCP policy to "Registry only" and populate the registry with approved servers
  4. Add a branch ruleset blocking MCP tool calls

Answer: C. The MCP allow list at org level (Settings > Copilot > Policies) controls which servers agents can reach. "Registry only" means only vetted servers resolve; everything else is blocked.

Q3. A workflow step needs to comment on the agent's PR and commit a fix. Which minimal permissions: block is correct?

  1. contents: write and pull-requests: write
  2. contents: write only
  3. write-all
  4. contents: read and pull-requests: write

Answer: A. Committing requires contents: write. Commenting on a PR requires pull-requests: write. D can't commit because contents is read-only. C works but violates least privilege.

Domain 4: Evaluation & Tuning

Q4. An agent resolves a CodeQL alert by adding a suppression comment instead of fixing the underlying vulnerability. What classification and fix apply?

  1. Tool misuse — remove the agent's access to CodeQL
  2. Context/environment — clear the context window and restart
  3. Reasoning error — revise instructions to explicitly forbid suppression
  4. Tool misuse — change permissions to read-only

Answer: C. The agent used the tool correctly. The error was in reasoning about what "resolve" means — it took the easiest path. Fix: make instructions explicit about intended behaviour. "Took a shortcut or misread the goal" = reasoning error.

Q5. A CodeQL check shows "Resource not accessible by integration" when trying to upload SARIF. What is most likely missing?

  1. The contents: write permission on the workflow
  2. The security-events: write permission on the analyze job
  3. The agent needs admin access to the repository
  4. Secret scanning must be enabled first

Answer: B. SARIF upload requires security-events: write on the job running codeql-action/analyze. This is the classic fix for that error message.

Domain 5: Multi-Agent Orchestration

Q6. A coder agent and a designer agent both modify the same CSS file on their isolated branches. How does GitHub-native arbitration resolve this?

  1. The orchestrator agent merges both changes automatically
  2. The second PR is automatically closed as a duplicate
  3. CODEOWNERS assigns the CSS path to a team who reviews both PRs and decides
  4. The concurrency group cancels the second agent's run

Answer: C. Multi-agent conflict resolution is GitHub-native: CODEOWNERS maps paths to owners, and when two PRs touch the same path, the human owners review both and decide. Agents never negotiate with each other.

Q7. An organisation wants to retire an agent without losing auditability. What is the correct approach?

  1. Delete the agent's .agent.md file and all its closed PRs
  2. Rename the agent's file to .agent.md.disabled
  3. Move the agent to a separate archive repository
  4. Remove the agent's profile but preserve its closed PRs and commit history

Answer: D. Retiring = remove the profile (so it's no longer invoked) + keep closed PRs, commits, and git history. This preserves auditability. Deleting PRs (A) destroys the audit trail.

Domain 6: Guardrails & Governance

Q8. An org wants to maximise delivery speed for agent-authored docs PRs while staying compliant. Which gate configuration is correct?

  1. Require CODEOWNERS review + environment approval + manual test sign-off
  2. No gates — docs are low risk
  3. Require automated checks (lint, link-check) to pass; no human review required
  4. Require Copilot code review only, skip all other checks

Answer: C. Velocity balance: docs are low-risk and reversible → automated checks suffice. A over-gates. B is non-compliant. D skips required status checks.

Q9. A ruleset requires 1 approving review with require_code_owner_review: true. The Copilot code review rule approves the PR. Can the PR merge?

  1. Yes — Copilot's approval satisfies the required review count
  2. No — Copilot's approval does not count towards required_approving_review_count; a human code owner must still approve
  3. Yes — if the code owner review requirement is met by any reviewer
  4. No — Copilot cannot review PRs opened by agents

Answer: B. Copilot code review is advisory only; its approval never satisfies required_approving_review_count or the code owner review requirement. A human must approve. One of the most likely exam questions verbatim.

Domain 3: Memory & State

Q10. An agent's session crashes mid-task after three commits on its branch. When a new session starts, what should the agent do first?

  1. Re-read the original issue and start implementation from scratch
  2. Ask the user what was completed before the crash
  3. Read the PR body, comments, checks, and commit history to reconstruct state
  4. Load the conversation history from the previous session

Answer: C. Sessions are ephemeral — conversation history doesn't persist. The durable record (PR, commits, checks, artefacts) is the agent's long-term memory.

Q11. An agent has been working on a long task and its outputs are becoming increasingly inconsistent with its plan. What is the correct response?

  1. Checkpoint current decisions into plan.md, reset the session, resume from the durable record
  2. Add the full PR conversation history to the context window for more detail
  3. Increase the model's context window size to fit more information
  4. Continue working — the agent will self-correct as it gets closer to completion

Answer: A. This is context rot. The fix: checkpoint (save decisions durably), prune/reset (clear the bloated window), and resume from the record. Adding MORE context (B, C) makes it worse.

Domain 1: Architecture & SDLC

Q12. A team configures their agent to analyse an issue, write code, open a PR, and request review — all in one continuous action. Which anti-pattern?

  1. Unbounded autonomy with no inspectable artefacts
  2. Execution without validation
  3. No separation between planning and execution
  4. Direct merge to main without review

Answer: C. The agent plans and executes in one uninterrupted flow with no plan-approval gate. A PR exists (so A is wrong). It requests review (so B/D don't apply). The missing boundary is between thinking and acting.

Cross-domain traps

Q13. An agent's PR has one human approval but CodeQL check is red. The agent dismissed the alert and requested review. Can it merge?

  1. Yes — a human approved, which overrides failing checks
  2. No — the required status check (CodeQL) is failing; the ruleset blocks merge regardless of approvals
  3. Yes — dismissing the alert clears the check
  4. No — Copilot must also approve before merge is possible

Answer: B. A required status check that is red blocks merge even with human approval. Rulesets enforce checks AND reviews. Human approval can't override a red required check.

Q14. A planner agent reads the codebase and produces a plan, then the same agent edits two files to "get started" before the plan is reviewed. What has gone wrong, and where is the fix?

  1. Memory issue (D3) — the agent forgot it was in planning mode
  2. Tool misuse (D4) — the agent used edit tools incorrectly
  3. Governance gap (D6) — add an environment gate before implementation
  4. Architecture violation (D1) enforced via tools config (D2) — the planner's tools: field should not include edit

Answer: D. The root issue is architectural: the planner shouldn't be able to edit. Enforcement: set tools: ['read','search'] in the agent profile. Don't fix architectural violations with governance gates — make the violation physically impossible.

Q15. Two agents work in parallel on the same concurrency group. Agent B starts a new run while Agent A's run is in progress. cancel-in-progress: true is set. What happens to Agent A's run?

  1. Both runs complete normally
  2. Agent A's run is queued and runs after Agent B finishes
  3. Agent A's in-progress run is cancelled
  4. Both runs are cancelled and a new consolidated run starts

Answer: C. With cancel-in-progress: true, a new run in the same concurrency group cancels the existing in-progress run. With false, the new run queues (one pending run max). D is invented behaviour.

Mnemonics

The lifecycle

PAE — "Plan, Act, Evaluate"

Cyclical. Any answer that codes before planning, or merges before evaluating, breaks PAE.

Branch discipline

NEVER MAIN

Own branch, one PR, checks + review decide. No exceptions.

Failure classification

RTE — "Reasoning, Tool, Environment"

R = misread goal, shortcut → revise instructions. T = wrong tool/params → refine tool access. E = missing var, token, context rot → fix env, scope memory, reset.

Permissions mechanism

SCOPE ZEROES

Specify one scope → every unlisted scope becomes none. Commit = contents: write. PR comment = pull-requests: write. SARIF = security-events: write.

Two gates, two places

MERGE ≠ DEPLOY

Rulesets + required checks guard the merge. Environment protection + required reviewers guard the deploy.

CODEOWNERS precedence

LAST WINS

Last matching pattern takes precedence. Put catch-all * first, specifics below. File found in .github/, then root, then docs/.

Config surfaces

CPR — "Cloud / Personal / Registry"

Cloud agent: repo Settings > Copilot > MCP (mcpServers, local). Personal IDE: .vscode/mcp.json (servers, stdio). Registry: org Copilot policies.

Memory model

CHECKPOINT, DON'T CRAM

Context window = short-term, dies with session. Platform record = long-term. Drift? Checkpoint, reset, resume from the record.
